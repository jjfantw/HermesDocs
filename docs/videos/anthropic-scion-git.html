EP434 - Anthropic 把 Git 換掉了！一天合併 3 萬次，Git 為什麼撐不住？｜Scion

📺 AI懶人報⏱ 10:06🗓 2026-10-17🌐 zh-Hant🔗 https://www.youtube.com/watch?v=P9NQhuktbIk

影片以 Anthropic 將主要程式碼倉庫從 Git 遷往自建系統 Scion 為主題，說明其背景是大量常駐線上的 AI agent 與自動化工作改變了版本控制的負載型態。片中指出，Anthropic 在九月單日合併超過 30,000 次，CI 每天約需 checkout 2,500 萬次；在此規模下，完整複本與鏡像伺服器的做法逐漸成為瓶頸。Scion 將資料集中於伺服器端，工作端按需快取或查詢，讓測試與研究工作所需的 checkout 從數分鐘縮短到數秒。影片也以七人、五個月完成 Scion 與相關系統的案例，討論 Claude 在開發中的角色；人類工程師仍負責判斷系統規則、拒絕不恰當的改動並審核意圖。影片的結論不是一般團隊應淘汰 Git：Scion 並非通用替代品；更實際的提醒是，當多個 agent 同時開發時，版本控制、建置與測試等原本按人類速度設計的流程可能先成為瓶頸。

01

Git 的設計假設，遇上大量常駐 agent

01:04

影片先回到 Git 的原始設計：每個工作者保有完整程式碼與歷史，因此離線仍可查看歷史與比對版本。

Anthropic 的情況則是大量會自行寫程式、跑測試的 agent 與自動化工作；影片認為，這些幾乎不離線的使用者使原本的完整複本設計成為負擔。

版本控制負載
02

高頻 merge 與 CI checkout 讓 Git 架構吃緊

01:49

片中引述九月單日超過 30,000 次 merge，平均不到三秒一次；CI 每日約需 checkout 2,500 萬次。

影片說明，當每次工作都要取得完整程式碼，而壓縮後的單份倉庫已超過 25 GB，即使用過淺層複製、部分資料夾與多台鏡像伺服器，仍會因更新速度與儲存資源遇到限制。

CI
03

Scion：把版本控制改成按需存取的伺服器模型

03:35

影片把 Git 比作寄附件：每個人都有完整副本；把 Scion 比作雲端文件：資料分散存於伺服器，工作端只保留少量快取並按需取得資料。

以修正結帳頁錯字為例，agent 可只取所需資料夾或檔案；比較版本等查詢也可能直接由伺服器回答。片中指出 commit 在伺服器端完成，因此沒有傳統 push 這一步。

Scion
04

AI 寫程式加速後，人類仍需做判斷與約束

05:22

影片描述七人團隊在五個月內完成 Scion、Antique 與相關系統，並搬遷主要倉庫；也舉例 Claude 重寫 Git 資料匯入程式後，保留未明文化的資料匯入順序規則。

片中對工程師角色的說法是「對 Claude 說不」：拒絕可能違反核心規則的捷徑，或避免防禦性審查導致不必要的複雜度。每項改動仍由人審核，但重點放在它想完成什麼。

工程審核
05

不必換掉 Git；先檢查人類速度的周邊流程

07:44

影片明確引述 Anthropic 的立場：Scion 不適合作為一般用途的 Git 替代品，且未開放下載；它面對的是極大型 monorepo 與大量 agent 的特殊規模。

對正在使用多個 agent 的團隊，影片建議先量化測試取得程式碼的頻率與時間、以意圖審核 AI 改動，並檢查版本控制與測試能否跟上開發速度。

實務建議
06

今天即可採用的隔離方式：git worktree

08:49

影片建議使用 Git 內建的 worktree，讓不同 agent 在同一份程式碼的獨立工作目錄中處理各自分支，降低互相覆蓋檔案的機會。

這些工作目錄共用歷史資料，完成後再合併回來；影片將其列為在不更換 Git 前可先採取的做法。

Git worktree

  1. git worktree add

當 AI 寫程式不再是瓶頸，先卡住的往往是版本控制、建置與測試等仍以人類速度為假設的流程。
